## Context

Upcoming uses one mixed ordering plane: ordinary tasks store `upcoming_order_key`, while recurrence prototypes store the same concept on their recurrence definition. The authoritative activation function currently evaluates due recurrences before activating ordinary reached Starts and deadlines. Generated recurrence instances are inserted directly into Today Inbox with the prototype's historical ordinary `order_key`; the later ordered activation loop skips them because their Inbox horizon is already set. Ordinary reached work is therefore ordered correctly relative to other ordinary work, but not relative to generated recurrence instances from the same Upcoming bucket.

The foreground repository also activates reached ordinary tasks without allocating fresh Inbox order keys, so offline/local presentation can temporarily disagree with the server's ordering behavior.

## Goals / Non-Goals

**Goals:**

- Preserve the exact mixed Upcoming sequence of ordinary tasks and recurrence prototypes when their work is realized on the same owner-local date.
- Append that newly realized sequence after work already retained or rolled into Today Inbox.
- Keep activation idempotent and retain the recurrence instance's generated Start and Deadline semantics.
- Make local ordinary-task activation preserve the same relative order while the authoritative recurrence evaluation catches up.

**Non-Goals:**

- Reorder tasks that were already in Today Inbox before the activation pass.
- Change recurrence cadence, catch-up policy, metadata inheritance, or prototype ordering behavior.
- Repair historical Today ordering after activation has already completed.

## Decisions

### Collect generated recurrence roots into the same activation batch

The authoritative activation function will collect the root task IDs returned by recurrence evaluations. It will then allocate fresh Today Inbox order keys in one loop containing both those generated roots and ordinary reached tasks, sorted by controlling date, `upcoming_order_key`, and stable ID.

This is preferred over assigning a prototype-derived ordinary `order_key` during recurrence insertion because an Upcoming rank is meaningful only relative to the other work in that reached date bucket. A direct insert cannot safely choose an Inbox key without seeing existing Inbox work and ordinary tasks that will activate later in the same transaction.

### Exclude the generated batch when locating the existing Inbox tail

Recurrence roots are initially inserted with Today Inbox membership to preserve current planning validation and generated Start semantics. When activation finds the Inbox tail, it will exclude roots generated by the current pass. The complete new batch can then be appended after pre-existing and rolled-over Inbox work without allowing provisional recurrence order keys to influence placement.

### Preserve recurrence Start while normalizing ordinary activation

The unified update retains the generated recurrence instance's persisted Start. Ordinary explicit Starts continue to clear when reached, while deadline-only ordinary tasks continue to materialize the current planning date as Start.

### Align local ordinary activation with the authoritative order contract

The foreground repository will read the current Inbox tail and assign sequential keys while activating its already Upcoming-sorted ordinary candidates. It cannot materialize recurrence instances offline, but it will no longer discard the user's ordinary Upcoming ordering while waiting for server convergence.

The authoritative pass will also recognize current-day native/system Inbox activations as provisional local work. It will exclude them from the retained Inbox tail, fold them into the mixed batch, preserve their already-normalized Start value, and mark the finalized server mutation as automation-authored. This makes a connected client that uploads its local midnight activation before the recurrence job converge through the same ordering pass without making later retries reorder the batch.

### Compare fractional keys with ordinal collation

Fractional-indexing keys are case-sensitive ordinal strings. The client compares them by code-point order, and the Upcoming database query uses PostgreSQL's `"C"` collation for the same reason. The activation function must explicitly use `"C"` for every fractional-key ordering operation. A database's default linguistic collation can otherwise place a lower-case key such as `aP` before upper-case keys such as `Zw` and `Zx`, producing a Today sequence different from the one displayed in Upcoming.

## Risks / Trade-offs

- [Risk] A generated recurrence root receives a second revision update during activation. → Mitigation: keep the update system-authored and in the same transaction, and cover retry idempotency so no later pass rewrites it.
- [Risk] Catch-up recurrence evaluation can generate more than one instance for one prototype. → Mitigation: retain controlling-date sorting before Upcoming rank and use stable IDs as the final deterministic tie-breaker.
- [Risk] Local ordinary activation briefly lacks recurrence rows while offline or before synchronization. → Mitigation: preserve ordinary relative order locally and rely on the existing authoritative server activation to converge the complete mixed batch.
- [Risk] A connected foreground client can upload an ordinary activation before the server recurrence pass. → Mitigation: treat current-day native/system Inbox activations as provisional until the authoritative pass marks the combined order automation-authored.
- [Risk] Database collation can differ from the ordinal comparison required by fractional indexing. → Mitigation: apply the `"C"` collation explicitly and cover upper- to lower-case key boundaries in pgTAP.

## Migration Plan

Add a forward-only migration replacing `tasks_private.activate_due_roots` with the unified batch allocation. The migration changes no table shape and requires no data backfill. Rollback consists of restoring the prior function definition, though already assigned Today order keys remain valid user data.
